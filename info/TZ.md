Техническое задание (ТЗ): Kanban-трекер задач

Версия: 1.0

Тип проекта: MVP веб-приложения

Назначение: разработка однопользовательского Kanban-трекера задач с современным интерфейсом, плавным Drag-and-Drop и локальным хранением данных.

Целевая среда: современные браузеры на ПК, планшетах и смартфонах.

1\. Цель и границы MVP

1.1. Цель проекта

Разработать веб-приложение для управления задачами на одной Kanban-доске. Пользователь должен иметь возможность создавать, редактировать, удалять, фильтровать и перемещать задачи между четырьмя фиксированными колонками.

Основной приоритет разработки — качественный пользовательский интерфейс в стиле Linear и безупречная механика Drag-and-Drop как для мыши, так и для сенсорного управления.

1.2. Основные возможности

•	Одна Kanban-доска с четырьмя фиксированными колонками.

•	Создание, редактирование и удаление задач.

•	Перемещение карточек между колонками и изменение их порядка.

•	Автоматическое изменение статуса при перемещении.

•	Автоматическая фиксация даты завершения задачи.

•	Назначение исполнителей из локального списка участников.

•	Три уровня приоритета.

•	Теги и сроки выполнения.

•	Поиск по названию и описанию.

•	Фильтрация по исполнителю и приоритету.

•	Возможность скрывать выполненные задачи.

•	Автосохранение данных в localStorage.

•	Импорт и экспорт данных в формате JSON.

•	Светлая и тёмная темы.

•	Адаптивный интерфейс для ПК, планшетов и смартфонов.

1.3. Ограничения MVP

Не реализовывать:

•	Регистрацию, авторизацию и разграничение прав доступа.

•	Серверную часть и удалённую базу данных.

•	Совместную работу пользователей в реальном времени.

•	Несколько проектов или досок.

•	Настраиваемые колонки и пользовательские статусы.

•	Вложения, чек-листы, подзадачи и комментарии.

•	Историю изменений и отмену действий через Ctrl+Z.

•	WIP-лимиты.

•	Уведомления и интеграции со сторонними сервисами.

Приложение должно работать без собственного backend. Данные принадлежат текущему браузеру и не синхронизируются между устройствами автоматически.

2\. Роли и сценарии

2.1. Роли

В приложении предусмотрена одна роль — пользователь доски.

Поскольку авторизация отсутствует, любой посетитель приложения может просматривать и изменять локальные данные.

Исполнители являются сущностями приложения, а не авторизованными пользователями. Их список хранится локально.

2.2. Основные пользовательские сценарии

Сценарий 1. Создание задачи

1\.	Пользователь нажимает кнопку «Создать задачу».

2\.	Открывается модальное окно.

3\.	Пользователь заполняет обязательные и необязательные поля.

4\.	Нажимает «Создать».

5\.	Задача появляется в колонке «Новая».

6\.	Данные сохраняются в localStorage.

Сценарий 2. Редактирование задачи

1\.	Пользователь нажимает на карточку.

2\.	Открывается модальное окно с заполненными данными.

3\.	Пользователь изменяет поля.

4\.	Нажимает «Сохранить».

5\.	Карточка обновляется, данные сохраняются.

Сценарий 3. Перемещение задачи

1\.	Пользователь начинает перетаскивание карточки мышью или касанием.

2\.	Интерфейс показывает состояние перетаскивания.

3\.	Пользователь перемещает карточку в другую позицию или колонку.

4\.	После отпускания карточка фиксируется в новом месте.

5\.	При смене колонки обновляется статус задачи.

6\.	Если задача перемещена в «Готово», фиксируется дата завершения.

7\.	Изменения сохраняются автоматически.

Сценарий 4. Удаление задачи

1\.	Пользователь открывает карточку.

2\.	Нажимает «Удалить».

3\.	Приложение запрашивает подтверждение.

4\.	При подтверждении задача удаляется.

5\.	При отмене задача остаётся без изменений.

Сценарий 5. Поиск и фильтрация

1\.	Пользователь вводит поисковый запрос или выбирает фильтры.

2\.	Доска отображает только подходящие карточки.

3\.	Счётчики показывают количество отображаемых задач.

4\.	Пользователь может сбросить фильтры и вернуть полный список.

Сценарий 6. Перенос данных

1\.	Пользователь открывает настройки.

2\.	Выбирает экспорт или импорт JSON.

3\.	При экспорте получает файл с данными доски.

4\.	При импорте выбирает файл.

5\.	Приложение проверяет структуру данных.

6\.	При корректном файле предлагает подтвердить замену текущих данных.

7\.	При ошибке показывает сообщение, не изменяя существующие данные.

3\. Структура данных

3.1. Модель задачи

Создать тип Task со следующими полями:

Поле	Тип	Обязательное	Описание

id	string	Да	Уникальный идентификатор

title	string	Да	Название задачи

description	string	Нет	Описание задачи

status	TaskStatus	Да	Текущий статус

priority	TaskPriority	Да	Приоритет

assigneeId	string | null	Нет	ID исполнителя

createdAt	string	Да	Дата и время создания в ISO 8601

dueDate	string | null	Нет	Срок выполнения в формате YYYY-MM-DD

completedAt	string | null	Нет	Дата и время завершения в ISO 8601

tags	string\[]	Да	Список тегов

position	number	Да	Позиция карточки внутри колонки

Дополнительные поля, не предусмотренные этим ТЗ, не добавлять без необходимости.

3.2. Статусы задач

Использовать фиксированный набор значений:

type TaskStatus =

&#x20; | "backlog"

&#x20; | "in\_progress"

&#x20; | "review"

&#x20; | "done";

Соответствие статусов колонкам:

Значение	Название колонки

backlog	Новая

in\_progress	В работе

review	На проверке

done	Готово

Статус задачи всегда должен соответствовать колонке, в которой она находится.

3.3. Приоритеты

type TaskPriority = "low" | "medium" | "high";

Визуальное представление:

•	low — зелёный или нейтральный серый.

•	medium — синий.

•	high — красный.

Цвет должен сопровождаться текстовой меткой или доступным описанием, чтобы значение приоритета не определялось исключительно по цвету.

3.4. Модель исполнителя

interface Assignee {

&#x20; id: string;

&#x20; name: string;

&#x20; color: string;

}

Требования:

•	Исполнители выбираются из локального списка.

•	Аватар формируется из инициалов имени.

•	Цвет аватара определяется стабильно на основе исполнителя.

•	Для задачи допускается отсутствие исполнителя (assigneeId: null).

•	При удалении исполнителя, если такая операция будет предусмотрена, задачи не должны терять корректность данных: их assigneeId необходимо обнулить.

Минимальный список участников должен быть доступен для выбора. Интерфейс управления участниками не входит в обязательный MVP, если он не реализуется без существенного усложнения. Если список нельзя изменять, использовать небольшой предопределённый набор участников и предусмотреть возможность его расширения в коде.

3.5. Модель доски

interface BoardData {

&#x20; version: number;

&#x20; tasks: Task\[];

&#x20; assignees: Assignee\[];

&#x20; settings: {

&#x20;   theme: "light" | "dark";

&#x20; };

}

Колонки задаются в коде как константы, а не хранятся в пользовательских данных.

Для каждой колонки необходимо определить:

•	Идентификатор статуса.

•	Название.

•	Порядок отображения.

•	Цветовой или визуальный акцент, если нужен дизайну.

3.6. Правила валидации

•	Название обязательно.

•	Название после удаления пробелов по краям не может быть пустым.

•	Описание необязательно.

•	Приоритет должен соответствовать одному из трёх допустимых значений.

•	Статус должен соответствовать одной из четырёх фиксированных колонок.

•	Срок выполнения необязателен.

•	Теги хранятся массивом строк, без пустых значений и дубликатов.

•	ID задачи уникален.

•	position используется для сохранения порядка карточек.

•	completedAt заполняется только для завершённых задач.

•	Даты проверяются на корректность до сохранения или импорта.

4\. Экраны и компоненты

4.1. Основной экран

Основной экран — одна Kanban-доска.

Структура:

1\.	Верхняя панель.

2\.	Панель поиска и фильтров.

3\.	Область Kanban-доски.

4\.	Модальное окно задачи.

5\.	Меню настроек с импортом и экспортом.

На широком экране колонки отображаются горизонтально. Если их суммарная ширина превышает ширину окна, область доски должна поддерживать горизонтальную прокрутку.

4.2. Верхняя панель

Содержит:

•	Название доски.

•	Поле поиска.

•	Фильтр по исполнителю.

•	Фильтр по приоритету.

•	Переключатель «Скрывать выполненные».

•	Кнопку «Сбросить фильтры».

•	Кнопку «Создать задачу».

•	Переключатель светлой и тёмной темы.

•	Доступ к настройкам импорта и экспорта.

На мобильных устройствах панель должна адаптироваться: фильтры могут сворачиваться в отдельное меню, но все функции должны оставаться доступными.

4.3. Kanban-доска

Доска состоит из четырёх колонок в следующем порядке:

1\.	Новая.

2\.	В работе.

3\.	На проверке.

4\.	Готово.

Каждая колонка содержит:

•	Заголовок.

•	Счётчик задач.

•	Список карточек.

•	Область приёма карточек при перетаскивании.

•	Пустое состояние, если карточек нет.

Колонки визуально различимы, но не должны перегружать интерфейс цветом.

Счётчик должен отражать количество задач, отображаемых в колонке с учётом активных фильтров. Если это приводит к неоднозначности, дополнительно можно показывать общее количество задач в колонке.

4.4. Карточка задачи

Карточка содержит:

•	Название.

•	Индикатор и текстовое обозначение приоритета.

•	Аватар исполнителя, если назначен.

•	Теги.

•	Срок выполнения, если задан.

Правила отображения:

•	Просроченный срок подсвечивается красным, если задача не завершена.

•	Завершённые задачи не считаются просроченными.

•	Длинное название ограничивается по количеству отображаемых строк с возможностью прочитать полное название в модальном окне.

•	Карточка имеет визуальные состояния default, hover, dragging, drop-target.

•	Клик по карточке открывает окно редактирования.

•	Начало перетаскивания не должно открывать модальное окно.

4.5. Модальное окно задачи

Окно используется для создания и редактирования задачи.

Поля:

•	Название.

•	Описание.

•	Приоритет.

•	Исполнитель.

•	Срок выполнения.

•	Теги.

•	Статус — при редактировании, если требуется ручная смена статуса в дополнение к Drag-and-Drop.

Дата создания формируется автоматически и не редактируется пользователем. Дата завершения управляется приложением автоматически.

Кнопки:

•	«Создать» — в режиме создания.

•	«Сохранить» — в режиме редактирования.

•	«Удалить» — в режиме редактирования.

•	«Отмена».

Поведение:

•	Esc закрывает окно.

•	Клик по затемнённому фону закрывает окно.

•	Клик внутри окна не закрывает его.

•	При наличии несохранённых изменений закрытие должно либо сохранять данные автоматически, либо предупреждать об их потере. Выбрать единый вариант реализации и применять его последовательно.

•	Удаление требует отдельного подтверждения.

•	Фокус при открытии переводится в поле названия.

•	При закрытии фокус возвращается на элемент, открывший модальное окно.

4.6. Фильтры и поиск

Поиск выполняется по названию и описанию задачи без учёта регистра.

Доступные фильтры:

•	Исполнитель.

•	Приоритет.

•	Скрытие завершённых задач.

Фильтры должны работать одновременно и пересекаться по логике AND.

Кнопка «Сбросить фильтры» очищает поисковый запрос и все активные фильтры, возвращая полный список.

Фильтрация не должна изменять исходные данные задач и их сохранённый порядок.

Если фильтры скрыли часть карточек, Drag-and-Drop не должен неожиданно менять порядок скрытых задач. Рекомендуемое поведение: при активных фильтрах отключить изменение порядка перетаскиванием либо обеспечить однозначное восстановление полного порядка после снятия фильтров.

4.7. Настройки и тема

Реализовать переключение между светлой и тёмной темами с использованием Tailwind CSS dark variant.

Требования:

•	Светлая тема используется по умолчанию.

•	Выбор темы сохраняется в локальных данных.

•	После перезагрузки применяется сохранённая тема.

•	Цвета текста, фона, границ, карточек, модальных окон и состояний Drag-and-Drop должны корректно работать в обеих темах.

4.8. Импорт и экспорт JSON

В настройках доступны действия:

•	«Экспорт в JSON».

•	«Импорт из JSON».

Экспорт должен формировать файл со всей необходимой структурой доски: версия схемы, задачи, исполнители и настройки.

Импорт должен:

1\.	Прочитать выбранный JSON-файл.

2\.	Проверить корректность JSON.

3\.	Проверить версию схемы и обязательные поля.

4\.	Проверить уникальность ID, статусы, приоритеты и даты.

5\.	Проверить ссылки на исполнителей.

6\.	Нормализовать порядок карточек при необходимости.

7\.	Запросить подтверждение замены текущих данных.

8\.	Применить данные только после успешной проверки.

При ошибке импорта показать понятное сообщение и сохранить текущие данные без изменений.

5\. Логика Drag-and-Drop

5.1. Основные требования

Drag-and-Drop — критически важная часть MVP.

Механика должна работать:

•	С мышью на компьютере.

•	С касаниями на смартфонах и планшетах.

•	При перемещении внутри одной колонки.

•	При перемещении между колонками.

•	При вертикальной прокрутке списков и горизонтальной прокрутке доски.

5.2. Выбор библиотеки

Использовать @dnd-kit/core и подходящие дополнительные пакеты @dnd-kit/sortable и @dnd-kit/utilities, если они совместимы с выбранной версией проекта.

Не реализовывать полноценную механику перетаскивания самостоятельно на базе нативных HTML Drag Events, поскольку требуется одинаковое поведение мыши и сенсорных устройств.

5.3. Визуальное поведение

При начале перетаскивания:

•	Карточка визуально приподнимается.

•	Добавляется тень.

•	Исходная карточка становится полупрозрачной.

•	Отображается плавающая копия карточки (DragOverlay).

•	Целевая колонка подсвечивается при допустимом наведении.

•	Остальные карточки плавно перестраиваются, показывая предполагаемую позицию.

Во время перемещения:

•	Положение карточек обновляется без резких скачков.

•	Целевая позиция определяется по фактическим координатам указателя или касания.

•	Прокрутка доски не должна блокироваться без необходимости.

•	На сенсорных устройствах должна быть возможность перетаскивания без случайного открытия модального окна.

После успешного перемещения:

•	Карточка фиксируется в новой позиции.

•	Исходная полупрозрачность сбрасывается.

•	Обновляются данные состояния.

•	Изменения автоматически сохраняются.

После неудачного перемещения:

•	Карточка возвращается на исходное место.

•	Статус и порядок остаются прежними.

•	Анимация возврата должна быть плавной.

5.4. Изменение порядка внутри колонки

При перемещении карточки внутри одной колонки:

1\.	Определить исходную позицию.

2\.	Определить целевую позицию.

3\.	Обновить массив задач соответствующей колонки.

4\.	Пересчитать position.

5\.	Сохранить новый порядок.

Порядок должен быть устойчивым: после перезагрузки карточки остаются в том же порядке.

5.5. Перемещение между колонками

При перемещении карточки из одной колонки в другую:

1\.	Определить исходный статус и колонку.

2\.	Определить целевую колонку.

3\.	Удалить задачу из исходной позиции.

4\.	Установить статус, соответствующий целевой колонке.

5\.	Добавить задачу в указанную позицию целевой колонки.

6\.	Пересчитать позиции в обеих колонках.

7\.	Обновить дату завершения, если изменился статус завершённости.

8\.	Сохранить результат.

5.6. Правила даты завершения

•	При первом переходе в done заполнить completedAt текущим временем.

•	При повторном перемещении внутри done не менять completedAt.

•	При переводе из done в другой статус очистить completedAt.

•	При повторном завершении после возврата в работу установить новое значение completedAt.

5.7. Обработка ошибок и отмены

Если карточка отпущена вне допустимой области:

•	Не менять данные.

•	Не менять статус.

•	Не менять порядок.

•	Сбросить визуальные состояния перетаскивания.

•	Вернуть карточку на исходное место с анимацией.

Не реализовывать отмену последнего действия через Ctrl+Z.

5.8. Сенсорное управление

Использовать сенсорный датчик TouchSensor или эквивалентный сенсорный механизм выбранной версии библиотеки.

Требования:

•	Настроить небольшой порог активации, чтобы отличать касание от начала перетаскивания.

•	Не запускать перетаскивание при обычном нажатии на карточку.

•	Сохранить возможность вертикальной прокрутки на мобильных устройствах.

•	Не блокировать горизонтальную прокрутку доски, когда пользователь пытается прокрутить её жестом.

•	Проверить корректность работы на iOS Safari и Android Chrome.

•	При необходимости использовать touch-action точечно, не отключая скролл всей страницы.

5.9. Автопрокрутка

При приближении перетаскиваемой карточки к краю прокручиваемой области должна запускаться автопрокрутка.

Области автопрокрутки:

•	Вертикальная — внутри колонки, если список длинный.

•	Горизонтальная — в области доски, если все колонки не помещаются на экране.

Скорость должна быть плавной и зависеть от близости указателя или касания к краю.

5.10. Устойчивость состояния

•	Не допускать дублирования карточек при перемещении.

•	Не допускать потери карточки при смене колонки.

•	Использовать стабильные ID.

•	Обновлять состояние иммутабельно.

•	Не менять статус до подтверждения успешного завершения перетаскивания.

•	Сохранять согласованность данных после каждого успешного действия.

7\. Хранение данных

7.1. Автосохранение

Использовать localStorage.

Рекомендуемый ключ:

kanban-board-data

После каждого успешного изменения данных сохранять актуальный объект BoardData.

Автосохранение должно охватывать:

•	Создание задачи.

•	Редактирование задачи.

•	Удаление задачи.

•	Перемещение карточки.

•	Изменение порядка.

•	Изменение статуса.

•	Обновление исполнителей, если они редактируются.

•	Изменение темы.

Поисковый запрос и временные состояния интерфейса необязательно сохранять.

7.2. Инициализация приложения

При запуске:

1\.	Прочитать данные из localStorage.

2\.	Проверить наличие данных.

3\.	Если данных нет, создать начальное состояние.

4\.	Если данные существуют, проверить их структуру.

5\.	Если данные некорректны, не перезаписывать их молча.

6\.	Показать понятное сообщение об ошибке и предоставить возможность восстановить начальное состояние либо импортировать корректный JSON.

Начальная доска должна содержать четыре фиксированные колонки. Допускается создать несколько демонстрационных задач для знакомства с интерфейсом, если это согласовано с выбранным дизайном. Альтернативно использовать пустую доску с понятным приглашением создать первую задачу.

7.3. Экспорт

Экспортировать полный объект BoardData в JSON с читаемым форматированием.

Имя файла, например:

kanban-board-YYYY-MM-DD.json

Экспорт должен включать все задачи, в том числе скрытые фильтрами и завершённые задачи.

7.4. Импорт

•	Принимать только корректный JSON.

•	Проверять структуру и типы полей.

•	Не доверять содержимому файла.

•	Отклонять некорректные статусы и приоритеты.

•	Проверять уникальность ID.

•	Проверять корректность ссылок на исполнителей.

•	Не допускать частичного применения импорта.

•	Запрашивать подтверждение перед заменой текущих данных.

•	Сохранять предыдущие данные при любой ошибке импорта.

7.5. Обработка ошибок хранения

Если localStorage недоступен или превышен лимит:

•	Не допускать падения приложения.

•	Показать понятное предупреждение.

•	По возможности сохранить текущее состояние в памяти до перезагрузки.

•	Предложить экспорт данных для сохранения вручную.

Не заявлять пользователю об успешном сохранении, если операция завершилась ошибкой.

7.6. Удаление данных

Удаление задачи всегда требует подтверждения.

Полное удаление данных доски допускается только через явно обозначенное действие с дополнительным подтверждением. Это действие не обязательно входит в основной интерфейс MVP.
